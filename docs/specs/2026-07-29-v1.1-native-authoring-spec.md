# Skill Engineering 1.1 Native Authoring Spec

状态：Accepted / In Progress

日期：2026-07-29

目标版本：`1.1.0`

## 背景

Skill Engineering 1.0 已经提供需求判断、创建计划、结构 Doctor、维护、评测、演进和发布安全，但真实用户在只安装 Agent Skill 的宿主中创建新 Skill 时，仍可能只得到通用脚手架：

- `SKILL.md` 只有通用输入、执行和输出段落；
- references、scripts、tests 或业务规则没有根据真实需求完成；
- 宿主缺少官方 `skill-creator` 时，创建链路可能提前停止；
- 结构检查通过后，宿主可能错误地把“骨架有效”报告为“Skill 已完整创建”；
- 普通用户仍被要求理解 Creator、CLI、Contract 或目录结构，偏离傻瓜式产品目标。

这个缺口已经在 Hermes 的真实使用中出现。它不是单一宿主兼容问题，而是 1.0 把“完整内容生成”部分交给外部 Creator、把确定性 fallback 定位成脚手架造成的产品边界错误。

## 1.1 产品决策

Skill Engineering 1.1 是创建、维护和管理 Agent Skill 的唯一用户入口。

用户只安装 Skill Engineering，即可在支持 Agent Skills 和基本文件操作的宿主中完成：

1. 描述需求；
2. 判断是否应该创建 Skill；
3. 逐步澄清真实任务；
4. 选择与风险匹配的架构；
5. 生成任务专属的完整 Skill 候选；
6. 检查结构、内容完整性、安全边界和资源引用，并获得评审分数；
7. 预览实际文件和内容；
8. 明确确认后写入；
9. 验证创建结果；
10. 使用真实任务试运行；
11. 根据失败案例继续维护、验证和撤销。

Skill Engineering 不得要求用户安装或调用 `skill-creator`、Hermes 专用作者 Skill，或其他宿主专用 Creator。

宿主原生的文件工具、审批工具或 Skill Manager 是执行适配层，不是内容生成依赖。

## 与官方 Skill Creator 的关系

1.1 必须完整覆盖官方 Skill Creator 的核心作者能力：

- 用具体示例理解 Skill；
- 规划需要的 scripts、references、assets 和界面元数据；
- 创建符合 Agent Skills 规范的目录和 `SKILL.md`；
- 编写完整、任务专属的 Skill 内容；
- 测试新增脚本；
- 校验 frontmatter、名称、描述和资源引用；
- 使用真实任务迭代；
- 更新已有 Skill。

在此基础上，Skill Engineering 继续提供 Creator 之外的能力：

- 先判断是否真的需要 Skill；
- 比较 Skill、Script、Plugin/runtime、项目规则或不新增产物；
- 选择 atomic、router、orchestrator、adapter 或 composite 架构；
- preview/apply 分离和同一计划防漂移；
- 副作用、审批、停止点和回滚契约；
- Doctor、行为证据、维护记录、自进化和发布门禁；
- 跨 Codex、Claude Code、Hermes、Pi、Kimi CLI 等宿主的统一入口。

用户可见定位必须使用准确表述：

> Skill Creator 主要帮助编写或更新一个 Skill；Skill Engineering 是跨宿主的完整生命周期入口，负责判断、完整创建、验证、维护和管理。

不得把官方 Skill Creator 错误描述为“只会创建骨架”，也不得继续把它列为 Skill Engineering 的创建依赖。

## 范围

### 进入 1.1

- 原生需求引导和 Authoring Brief；
- 原生完整候选生成；
- 内容完整性门禁；
- 单安装可用的基础候选检查和安全应用能力；
- 创建后对新建 Skill 的 Doctor 评审、评分与自然语言反馈；
- 创建后简易自动化测试入口（结构/内容门禁复跑、脚本测试、样例任务试用）；
- Codex、Claude Code、Hermes、Pi、Kimi CLI 的宿主适配契约；
- Hermes `skill_manage` 创建、补充文件、审批和安全扫描适配；
- 无 `skill-creator`、无独立 Python CLI 环境的核心创建闭环；
- 1.0 创建 CLI/API 的兼容和明确降级语义；
- 官方 Creator 能力覆盖矩阵；
- README、产品定位、架构、版本、测试和发布证据同步。

### 不进入 1.1

- 创建后的持久化 `README.md` 注释文档；
- Skill Read Guided Tour；
- 完整交互式 Skill Graph、本地 Web 图谱或 VS Code 图谱；
- 通用代码知识图谱；
- 新的云端服务、模型 Provider 或托管平台；
- 自动 Global 安装；
- 2.0 Architecture Guardian 的新能力。

创建后阅读、注释和图谱进入 `1.2.0`。1.1 可以在对话中简要说明创建结果，但不得为了赶进度建立未来需要废弃的第二套图谱事实模型。

## 目标用户体验

### 第一次创建

用户只需说：

> 帮我做一个能够把会议记录整理成决策、负责人和截止时间的 Skill。

Skill Engineering 自动完成已有能力扫描，然后一次只询问一个会改变结果的问题。已有上下文足够时跳过提问。

在写入前，用户至少能看到：

- 推荐名称和职责；
- 触发和反触发；
- 输入、输出和失败行为；
- 是否包含脚本、参考资料、模板、测试或外部操作；
- 将创建的全部文件；
- 每个文件中的实际业务内容摘要；
- 仍未验证的真实效果。

用户确认的是实际文件和行为，不是内部 Plan ID。

### 创建完成

只有以下条件都满足时，才能报告“Skill 已创建”：

- 计划内文件全部写入；
- 没有未解释的占位符或空资源；
- frontmatter、名称和描述有效；
- 所有显式引用可以解析；
- 必要脚本已经运行测试；
- lint 和基础 Doctor 没有阻断项，评审分数和等级已用自然语言告知用户；
- 创建后的目标与用户预览一致。

如果尚未进行真实任务试用，只能说明“结构和内容候选已完成，实际任务效果尚未验证”。

### 真实试用

创建后必须给出一个与用户需求一致的真实试运行入口。用户可以立即提供样本，也可以稍后恢复 Journey。

真实任务失败时，进入现有 improve 流程：

- 记录失败模式；
- 判断根因层级；
- 生成独立候选；
- 增加回归依据；
- 预览后应用；
- 验证并保留撤销入口。

## Native Authoring Kernel

1.1 在 Skill Engineering 自身内部拥有完整作者方法，不再 delegate 给其他 Creator。

### Authoring Brief

候选生成前，宿主 Agent 必须形成结构化、可检查的 Authoring Brief，至少包含：

- `goal`：用户反复需要完成的真实任务；
- `target_users`：谁使用以及复用范围；
- `positive_triggers`：应该触发的请求；
- `negative_triggers`：不应该触发的请求；
- `inputs`：必需输入、可选输入和来源；
- `outputs`：输出形状、完成条件和证据；
- `workflow`：任务专属步骤和分支；
- `failure_modes`：信息不足、工具失败和部分成功；
- `side_effects`：文件、网络、外部系统和不可逆动作；
- `approvals`：哪些动作必须确认；
- `resources`：scripts、references、assets、templates 和 tests；
- `examples`：至少一个成功示例，以及风险需要时的失败或反例；
- `verification`：结构检查、脚本测试和真实任务试用；
- `host_requirements`：需要的工具能力，不硬编码单一宿主名称。

Authoring Brief 保存脱敏摘要，不保存凭证、完整私有会话或原始敏感 Prompt。

### 架构选择

根据 Brief 自动选择最小架构：

- `atomic`：单一职责，简单 Skill 可以只有完整的 `SKILL.md`；
- `router`：只负责选择目标能力，不泄漏子能力实现；
- `orchestrator`：拥有跨阶段状态、部分失败和聚合；
- `adapter`：把宿主工具、MCP、API 或文件格式映射成稳定接口；
- `composite`：多个正交工具或能力的集合。

简单不等于简陋。只有一个 `SKILL.md` 时，该文件仍必须包含足以完成真实任务的专属规则、工作流和边界。

### 完整候选生成

宿主 Agent 根据 Brief 直接生成独立候选目录。候选必须包含完成真实任务所必需的全部内容：

- `SKILL.md`；
- 需要时的 `agents/openai.yaml`；
- 复杂、生产或有副作用 Skill 的 `skill.contract.yaml`；
- 需要按需加载的 `references/`；
- 需要确定性执行的 `scripts/`；
- 需要复用的 `assets/` 或 `templates/`；
- 需要防止回退的测试用例。

不得先把空骨架写入正式目标，再把补内容留给用户或下一次任务。

## Content Completion Gate

1.1 新增独立于结构 Doctor 的内容完整性检查。

### 确定性阻断

以下任一情况存在时，候选不得进入 Apply：

- `TODO`、`TBD`、`FIXME`、`placeholder` 或“稍后补充”等占位内容；
- 空的 references、scripts、assets、templates 或 tests；
- `SKILL.md` 仍包含 fallback 通用语句，例如“执行这个 Skill 拥有的单一职责”；
- 引用了不存在的文件、命令、工具或 delegate；
- 声明脚本但脚本不存在或没有对应验证；
- name、description、目录名或 frontmatter 不符合目标宿主共同支持的 Agent Skills 基线；
- 有副作用却没有 preview/approval/stop；
- 复杂工作流没有失败或部分成功处理；
- 候选包含凭证、私钥、cookie、`.env` 值或完整私有对话。

### 语义检查

宿主 Agent 必须逐项证明：

- 每个工作流步骤都与用户任务相关；
- 输入可以沿明确路径产生输出；
- 触发和反触发能够区分相邻任务；
- 用户提供的关键约束都落在候选文件中；
- 每个资源文件有明确读取或执行入口；
- 失败状态不会被包装成完整成功；
- 生成内容不是把 Authoring Brief 改写成更长的泛化 Prompt。

语义检查结果进入预览摘要，但不能冒充真实行为效用。

## 创建评审与评分

1.1 把评审作为创建主链路的固定步骤，不是创建后的可选动作。

### 触发时机

候选写入并通过结构 postflight 后，宿主 Agent 必须对新建 Skill 完成一次创建评审：

- 运行内容完整性门禁（确定性阻断 + 语义检查）；
- 运行 Doctor v2 结构评审，产出 0-100 分数、A-F 等级和功能价值、稳定性、安全、工程化四个维度的明细；
- 汇总用户仍需知道的边界：未覆盖的失败路径、尚未验证的真实效果和可选的后续改进。

### 用户可见反馈

评审结果必须用自然语言呈现，结论先行：

- 先说明：是否可以开始使用、分数和等级、最需要关注的一两个维度；
- 分数只能表述为“结构和工程就绪度”；没有真实任务试用前，必须同时说明“尚未验证实际任务效果”；
- 存在 FAIL 或 SEC 规则命中时，创建状态不得高于 `candidate_incomplete`，并给出唯一修复入口；
- 规则命中、维度明细和修复建议折叠进“技术详情”，不强迫小白用户阅读。

### 与既有评审体系的关系

- 创建评审复用现有 Doctor v2 规则与质量评分标准，不新建第二套评分模型；
- 创建评审是 `created_untried` 的组成部分；至少一个真实任务试用通过后才进入 `validated`；
- 评审分数不得跨 Skill 排名，不得描述为业务价值分，也不得被包装成官方 Skill Creator 不具备的“效果证明”。

## 单安装与 Portable Runtime

### 核心原则

通过标准 Agent Skill 安装入口安装 `skill-engineering` 后，普通用户完成核心创建流程不得再安装：

- 官方 `skill-creator`；
- Hermes 专用作者 Skill；
- Skill Engineering 独立 Python CLI；
- 其他 Creator、Plugin 或 MCP。

### 随 Skill 交付

Skill Engineering 包内必须包含创建闭环所需的可移植资源：

- Authoring Brief 和候选生成指令；
- 宿主能力探测与适配说明；
- 内容完整性检查器；
- 候选清单、fingerprint 和预览格式；
- 安全写入和写后验证入口；
- 缺少确定性运行条件时的 Agent-native 等价检查。

现有 Python 包可以继续服务高级开发、CI、评测和发布，但不能是普通用户完成核心创建的前置依赖。

## 宿主适配契约

### 共同能力

1.1 不按品牌编写五套作者方法。Native Authoring Kernel 只依赖能力：

- 读取项目规则和已有 Skill；
- 创建隔离候选；
- 展示候选内容或 diff；
- 请求用户确认；
- 创建目录和文件；
- 运行可用的基础检查；
- 读取写后结果。

### Hermes

- 使用 `skill_manage(create)` 写入完整 `SKILL.md`；
- 使用 `skill_manage(write_file)` 添加 supporting files；
- `skills.write_approval` 开启时尊重 Hermes pending/diff/approve 流程；
- 使用 Hermes 安全扫描结果作为额外门禁；
- 不调用 `hermes-agent-skill-authoring` 或 `/learn` 生成内容；
- 外部 Skill 目录和 Profile 范围必须显式识别，避免写错目标。

### Codex、Claude Code、Pi、Kimi CLI

- 使用宿主提供的文件编辑、终端和审批能力；
- 优先创建在当前项目的标准 Skill 目录；
- 用户要求共享或全局范围时，先展示实际目标和影响；
- 宿主不支持某项可选元数据时保留共同基线，不伪造支持；
- 不因工具名不同复制作者逻辑。

新增宿主通过 capability adapter reference 扩展，不修改 Native Authoring Kernel。

## 1.0 兼容与迁移

- 保持 1.0 已发布 CLI、JSON 和 contract 的兼容读取；
- 现有 flag-based `create` fallback 不删除，但必须明确标记为 `scaffold_only`；
- `scaffold_only` 不得产生“完整创建成功”的用户反馈；
- 1.1 新建主链路从完整候选生成不可变计划；
- Apply 仍引用用户预览的同一份未漂移计划；
- 旧计划可以按 1.0 语义读取，不能无提示升级成 `content_complete`；
- improve、verify、undo、evaluate、evolve 和 release 继续使用现有单一事实源。

## 用户可见完成状态

内部状态可以结构化，但用户只看到自然语言结论：

1. `needs_discovery`：还缺少会改变结果的信息；
2. `candidate_incomplete`：候选存在，但仍有内容缺口；
3. `candidate_ready`：完整候选和预览已准备，尚未写入；
4. `created_untried`：已按预览写入并通过创建检查，尚未验证真实任务效果；
5. `validated`：至少一个真实任务已完成，并有对应证据；
6. `needs_improvement`：真实失败已记录，等待候选修复。

不得把 `scaffold_only`、`candidate_incomplete` 或 `created_untried` 写成“已经验证有效”。

## 1.1 验收用例

### Case A：简单 atomic Skill

输入：将会议记录提取为决策、负责人和截止时间。

要求：

- 不依赖官方 Creator；
- 生成任务专属 `SKILL.md`，不是通用执行模板；
- 明确证据边界、缺失字段和反触发；
- 用户确认前不写正式目标；
- 写后可以使用真实会议记录试运行。

### Case B：带确定性脚本的 Skill

输入：把固定格式日志转换成稳定 JSON 报告。

要求：

- 自动判断解析器应进入 scripts；
- 生成并真实运行脚本测试；
- `SKILL.md` 清楚说明何时执行脚本；
- 脚本失败不能报告任务完成；
- 整个创建流程只依赖安装的 Skill Engineering 和宿主基础工具。

### Case C：有外部副作用的 adapter/orchestrator

输入：预览并同步内容到外部草稿系统。

要求：

- 明确 Plugin/runtime 与 Skill 的边界；
- 创建 preview/apply、审批、失败和部分成功契约；
- 没有凭证时仍可完成安全 Skill 候选，但不能伪造真实发布验证；
- high-risk case 和回滚入口存在。

### Case D：Hermes 无 Creator 环境

环境：

- 只安装 Skill Engineering；
- 不安装官方 `skill-creator`；
- 不调用 `hermes-agent-skill-authoring` 或 `/learn`；
- 允许使用 Hermes `skill_manage`。

要求：

- 完成需求澄清、完整候选、预览、写入和验证；
- `skill_manage(create)` 接收完整 `SKILL.md`；
- supporting files 使用 `write_file` 写入；
- 不在骨架阶段提前结束；
- 写审批开启时能进入 pending/diff/approve，而不是绕过。

### Case E：跨宿主共同候选

同一 Authoring Brief 分别在 Codex、Claude Code、Pi 和 Kimi CLI adapter fixture 中执行。

要求：

- 核心文件语义保持一致；
- 只有路径、工具调用和可选元数据发生宿主适配；
- 不要求安装宿主专用 Creator；
- 共同基线 Skill 可以迁移到另一个 Agent Skills 兼容宿主。

### Case F：创建后简易自动化测试

输入：完成创建（例如 Case A 的会议记录 Skill）后，用户说“帮我确认这个 Skill 真的能用”。

要求：

- 创建完成时自动生成最小自动化测试入口，用户只需一句话或一条命令即可复跑；
- 测试至少覆盖：结构与内容完整性门禁复跑、声明脚本的真实执行、一个与用户需求一致的样例任务；
- 测试通过是进入 `validated` 的证据之一；失败必须进入 `needs_improvement`，不得包装成成功；
- 不依赖第二次安装：宿主有 Python 时运行随 Skill 交付的 portable checker，没有 Python 时使用 Agent-native 等价检查；
- 测试结果用自然语言反馈，技术细节折叠进“技术详情”。

## 测试和证据

1. 修改 Skill 指令前，先保留 Hermes“只生成骨架并提前完成”的失败场景作为 RED 基线；
2. Skill 行为测试至少覆盖：
   - 无外部 Creator；
   - 小白用户只描述目标；
   - 信息不足；
   - 简单 Skill 只有一个文件但内容完整；
   - 复杂 Skill 需要 supporting files；
   - 副作用审批；
   - 宿主工具缺失；
   - 候选带占位符；
   - 用户要求立即写入造成的时间压力；
3. Python 实现遵循测试先行，先观察新增测试因缺少能力失败；
4. 运行 pytest、Ruff、Skill validation、credential lint、diff check；
5. 对 Skill Engineering 自身运行 production Doctor；
6. 在无 Creator 的隔离环境完成至少一次真实创建；
7. 静态通过只证明结构和内容门禁，不证明跨模型真实效用；
8. 每个验收 Case 的创建终点都包含创建评审分数反馈，且分数未被表述为真实任务效果；
9. 发布前必须记录 Codex 无 Creator 真实 E2E；Claude Code、Hermes、Pi、Kimi
   CLI 至少完成 adapter contract fixture，真实 smoke 作为非阻断兼容性证据
   （见 ADR-0009）。

## 发布门禁

满足以下条件前不得发布 `1.1.0`：

- 主 Skill 和 contract 中不存在 `official skill-creator` delegate；
- 普通用户文档不再要求第二次安装 Creator 或 Python CLI 才能完成创建；
- 标准 Agent Skill 安装产物包含 Native Authoring Kernel、adapter references 和核心检查资源，不依赖仓库外文件；
- Content Completion Gate 能阻断通用骨架、占位符和断链资源；
- 创建主链路包含创建评审与评分步骤，评审反馈在 Case A–F 证据中固定，且评分未被包装成真实任务效果；
- Case A–F 全部满足各自证据要求；
- 1.0 CLI/API/JSON 兼容回归通过；
- 全量 pytest、Ruff、Skill validation、production Doctor、credential lint 和 diff check 通过；
- Codex 无 Creator 真实 E2E 通过；这是默认唯一必须通过的真实宿主 E2E；
- Claude Code、Hermes、Pi、Kimi CLI adapter contract fixture 通过；这些宿主的
  真实 smoke 是非阻断兼容性证据；
- 独立评审确认“结构通过”没有被包装成“真实效果有效”；
- README、Product、Architecture、Roadmap、Task、Sprint、Version、Changelog 和测试证据一致；
- commit、push、tag 和公开发布分别获得明确授权。

## 成功标准

1. 普通用户只安装 Skill Engineering，并只描述目标，就能得到任务专属的完整 Skill，而不是通用骨架；
2. 宿主没有任何 Creator 时，创建流程仍能完成；
3. Skill Engineering 覆盖官方 Skill Creator 的理解、资源规划、内容编写、脚本测试、校验和迭代能力；
4. 同一作者内核可以通过 adapter 工作在 Codex、Claude Code、Hermes、Pi 和 Kimi CLI；
5. 任何占位、空资源、通用 fallback 或未解析依赖都会阻止 Apply；
6. 创建结果可以继续进入现有维护、评测、演进、发布和撤销流程；
7. 1.1 没有把 1.2 的阅读、注释和图谱偷偷塞回范围；
8. 每个新建 Skill 在创建完成时都获得结构、内容、安全和工程化的评审与分数反馈，且评分不被包装成真实任务效果。
