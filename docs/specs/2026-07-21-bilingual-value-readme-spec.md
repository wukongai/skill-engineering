# 双语价值型 README 改版规格

状态：Superseded by `2026-07-21-readme-product-reset-spec.md`

日期：2026-07-21

## 背景

当前根 README 以英文功能与版本说明为主，能够说明“项目有什么”，但没有在首屏清楚回答：

- Skill Engineering 为谁创造什么结果；
- 它与普通 Skill 模板、Prompt 生成器和一次性静态检查有什么本质差异；
- 为什么真实用户应当在第一次创建 Skill 时就使用它；
- 已经有哪些真实案例和发布证据支撑这些价值主张。

用户要求将仓库入口改为中文主版本与英文独立版本，并以“个人选题 Skill 改造”文章的叙事为核心，加入既有四个 1.0 Use Case，采用成熟高星开源项目常见的价值优先 README 结构。

## 用户与核心价值

### 目标用户

- 只会描述业务目标、不了解 Skill 工程规范的普通用户；
- 希望把个人经验沉淀为可复用 AI 能力的创作者和一人团队；
- 维护多个 Skill、担心反复修改造成架构腐化的开发者与团队；
- 需要契约、评测、审批、发布和回滚证据的商业或工业场景。

### 首屏价值主张

Skill Engineering 不是帮用户多写一个 `SKILL.md`，而是把真实经验变成从第一版起就可维护、可验证、可演进的 AI 能力资产。

### 差异化

1. **先判断，再生成**：先判断需求应该成为 Skill、Script、Plugin/runtime、项目规则，还是不新增产物。
2. **从第一版开始工程化**：在生成时就建立边界、架构、安全和验证入口，不等 Skill 变乱后再治理。
3. **全生命周期抗腐化**：修改通过独立候选、不可变预览、复杂度检查、回归证据、验证和撤销完成。
4. **证据先于宣传**：结构健康、行为证据和真实效用分开表述，不把 Doctor 分数冒充业务结果。

## 信息架构

中文 `README.md` 与英文 `README.en.md` 必须包含等价的信息层次：

1. 页首语言切换、稳定版本与许可证；
2. 一句话价值、适用用户和首要行动；
3. 以“50 条热点不等于好选题”为引子的真实改造故事；
4. Skill Engineering 的工作方式与用户结果；
5. 四个已经通过 1.0 发布回归的案例；
6. Agent Skill 优先的快速安装与自然语言使用示例；
7. Python CLI 与源码开发的独立安装路径；
8. 当前 Stable、2.0 Preview 和未来方向的准确边界；
9. 验证证据、产品边界、文档入口、贡献、安全与许可证。

## 案例要求

### 核心故事

选题雷达案例用于解释方法论，不宣称它是本仓库内置或已发布的 Skill：

- 原始系统能够搜索、打分和输出 Top 10，但“搜得多”不等于“值得由我来写”；
- 改造重点是个人证据、独立来源、职责边界、状态流转和持续评测；
- 由此证明 Skill Engineering 的价值是把个人判断沉淀成可维护系统，而不是堆更多提示词。

### 已验证案例

必须展示并链接 `docs/testing/2026-07-18-v1-use-cases.md` 中的四个案例：

- 会议纪要行动项；
- GitHub Issue 实施计划；
- 本地 Web 应用验收；
- 多文件研究证据包。

每个案例至少说明用户目标、工程化边界与最终价值。不得把确定性回归夸大为跨所有模型和生产环境的普遍效用证明。

## 版本与营销事实边界

- 当前稳定版本只能写为 `1.0.0` Stable Lifecycle Contract；
- `2.0.0` Architecture Guardian 只能写为开发预览；
- Behavior Eval Lab、Observation Boundary、Portfolio/Distribution 等只能写为未来探索或 Backlog，不宣称已经交付；
- 仓库当前没有正式 `3.0` 版本事实源，因此 README 可以表达完整长期愿景，但不能虚构 `3.0` 的发布范围或时间；
- Python CLI 与 Agent Skill 是独立交付物，安装一个不会自动安装另一个；
- 不宣称已发布 PyPI 包，不宣称自动 Global 发布，不宣称静态检查等于真实任务效果。
