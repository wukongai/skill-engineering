## 目标

在不依赖官方 `skill-creator`、Superpowers、宿主专用 Creator、Plugin/MCP 或独立 Skill Engineering CLI 的前提下，修复 Codex 交叉评审确认的 1.1 发布阻断项，使只安装 `skill-engineering` Agent Skill 的普通用户能够完成：

1. 保存脱敏的需求摘要；
2. 生成任务专属完整候选；
3. 对候选执行安全、可移植的内容门禁；
4. 预览不可变候选计划；
5. 明确确认后应用同一份未漂移计划；
6. 获得可复现的创建评审分数与等级；
7. 真实运行声明的自测；
8. 使用真实样本验证并在失败后进入 improve。

本 Spec 先修复 K3 实现的 review 缺口。完整的内部 Brainstorm → Skill Spec → 程序/测试 → Skill 作者流程作为紧随其后的第二阶段，不混入本修复候选。

## 产品边界

- Skill Engineering 是用户创建、维护和管理 Skill 的唯一入口。
- Superpowers 的需求澄清、Spec 和测试先行思想可以内化为 Skill Engineering 自身方法，但用户不得被要求安装、调用或理解 Superpowers。
- 官方 `skill-creator` 可以作为能力对比对象或维护者可选验证工具，不能进入普通用户创建主链路。
- 现有 Python CLI 保留高级维护、评测、CI 和 1.0 兼容能力，不能成为 1.1 核心创建闭环的前置安装。
- 读取、写入、终端和审批等宿主原生工具属于 capability adapter，不属于外部作者依赖。

## 修复范围

### R1：Native Authoring 主路由

普通创建必须全程使用 Native Authoring，不再跳转到 legacy `skill-engineering create`。

- 根 `SKILL.md` 明确：legacy `create` 只在用户明确要求 1.0 兼容或 CI scaffold 时使用；
- 普通创建生成完整候选后进入 portable candidate plan；
- 不得把 `scaffold_only` 计划升级或包装为完整候选。

### R2：Portable Candidate Plan

随 Skill 交付标准库脚本 `scripts/native_plan.py`，提供：

```text
preview --project <project> --brief-id <id> --candidate <dir> --target <dir> --plan <plan.json>
apply --plan <plan.json> --candidate <dir> --target <dir>
verify --plan <plan.json> --target <dir>
```

计划至少保存：

- schema/version；
- `.skill-engineering/authoring-briefs/` 中已持久化的 Brief id 与脱敏 Brief fingerprint；
- candidate 根目录、文件清单、每文件 SHA-256 与整体 fingerprint；
- target 和 target 创建前 fingerprint；
- Content Gate 结果；
- preview 时产生且不再修改的候选创建评审摘要；
- `content_status=content_complete`；
- preview 摘要；
- apply/verify 状态与执行时间。

约束：

- preview 只写 plan，不写正式目标；
- preview 不接受游离 Brief JSON，只接受项目状态目录中已经过持久化脱敏的 `brief-id`；
- candidate、Brief、target 或 plan 任一漂移时 apply 拒绝；
- candidate 内存在 symlink、越界路径或非普通文件时拒绝；
- target 已存在时拒绝覆盖；
- apply 使用 `mkdtemp` 在 target 同级创建唯一临时目录，复制并复验 fingerprint 后再原子改名；
- apply 失败清理本次临时目录，不删除用户原有目标；
- verify 只读取并比较 plan 与 target，不修改目标。

plan hash 覆盖所有决定文件、目标和完成语义的 immutable 字段，包括 Brief/candidate/target fingerprint、文件清单、Content Gate、候选创建评审、`content_status` 与 preview 摘要。只有 `applied`、`verified`、apply/verify 记录和执行时间不参与 plan hash；这些可变字段不得改变文件范围、评审结论或完成语义。

威胁模型与现有 1.0 BuildPlan 一致：fingerprint 和 plan hash 防止无意漂移与陈旧计划，不防止能够修改 plan 并重算 hash 的恶意受信宿主；宿主 Agent 是执行边界内的受信主体。候选内容、外部输入和目标现状仍按不受信数据处理。

没有 Python 的宿主使用 adapter 中的 Agent-native 等价清单，必须展示同一文件清单和 fingerprint 事实，不得凭聊天记忆 Apply。

### R3：Authoring Brief 持久化脱敏

`save_authoring_brief()` 是安全边界：

- 保存前自动调用脱敏逻辑；
- 磁盘状态不得包含原始凭证值；
- 原始调用对象不被静默修改；
- 私钥、Bearer、cookie、session、token、password、常见 API key 和 `.env` 赋值形态必须脱敏；
- 测试直接检查磁盘 JSON，不只测试 helper 返回值。

### R4：Content Completion Gate

`content_gate.py` 必须补齐以下确定性阻断：

- 任意 symlink；
- 引用 normalize/resolve 后逃出候选根目录；
- 引用目标不是候选内普通文件；
- `.env`、`.env.*`、`*.env` 与常见私钥/证书文件；
- 可解码文本中的私钥、token、cookie、password，不依赖少量扩展名；
- frontmatter `name` 与候选目录名不一致；
- 英文和中文的写入、删除、上传、发布、同步、网络请求、邮件发送等副作用没有 preview/approval/stop；
- 声明脚本没有对应自测 manifest；
- 自测 manifest 引用越界、symlink 或不存在的 fixture/script。

二进制资产不按文本扫描，但文件名、安全路径和 symlink 规则仍适用。读取失败必须产生 finding，不能按空字符串静默通过。

### R5：Portable Creation Review

随 Skill 交付标准库脚本 `scripts/creation_review.py`：

```text
python3 scripts/creation_review.py <skill-dir> --profile <personal|team|production> --json
```

输出至少包含：

- status 与退出码；
- 0–100 structural-readiness 分数；
- A–F 等级；
- 功能价值、稳定性、安全、工程化四个维度；
- findings 与 remediation；
- assessment coverage；
- `utility_claim=false`；
- 尚未完成的真实样本验证。

创建评审不是第二套效果评分。它是 Doctor v2 评分 rubric 的 portable creation profile，共用功能价值/稳定性/安全/工程化四个维度、20/25/25/30 权重和 A–F 等级阈值。规则集显式限定为可移植创建子集：frontmatter、触发边界、资源入口、副作用审批、失败处理和安全文本扫描。

仓库内维护枚举的 parity fixture 清单，portable creation profile 与 Doctor v2 只在该共同支持的 fixture 集上要求：

- PASS/FAIL 一致；
- grade 一致；
- 四维分数一致。

不对 Doctor v2 全部规则作全称分数 parity 承诺。高级 contract/evaluation/provider 规则只有完整 CLI Doctor 支持时作为可选增强；缺少 CLI 时必须说明 assessment coverage，不能伪装成已检查。fixture 清单和共同 rubric 是防止 portable profile 漂移的事实源，不另建效果评分模型。

### R6：受控的真实脚本自测

新 Skill 使用 `tests/self-test.json` 声明可复跑测试，格式为：

```json
{
  "schema_version": "1.0",
  "tests": [
    {
      "id": "success",
      "script": "scripts/example.py",
      "stdin": "tests/fixtures/input.txt",
      "expected_exit": 0,
      "stdout_contains": ["expected"],
      "timeout_seconds": 10
    }
  ]
}
```

`skill_self_test.py` 必须：

- 先运行 Content Gate 与 portable creation review；
- 只执行 manifest 显式声明的候选内脚本；
- 第一版 portable runner 支持 Python 脚本，使用当前 `sys.executable`；
- 只接受候选内普通文件，拒绝 symlink、绝对路径和 `..`；
- 在隔离临时副本中执行，清理环境变量，仅保留最小系统环境；
- 支持 stdin fixture、expected exit、stdout/stderr contains 与 JSON key 检查；
- 设置 1–30 秒 timeout；
- 不在被测 Skill 内生成 `__pycache__` 或其它文件；
- 任何测试失败返回 blocked，并要求进入 `needs_improvement`；
- 样例任务层仍由宿主 Agent 使用真实用户样本完成，不能由编译成功替代。

1.1 portable runner 不是操作系统沙箱：它以当前用户权限运行，不能阻断网络、子进程或强制 CPU/内存上限。最小缓解是 Content Gate 与 portable creation review 的静态安全检查先于执行、manifest 只允许候选内显式 Python 脚本、临时副本、最小环境和 timeout；命中网络、外部副作用或危险执行规则的候选不得进入自测。非 Python 声明脚本报告“portable runner 未覆盖”，不得静默跳过或报告通过。

没有 self-test manifest 但声明了脚本时，Content Gate 阻断。没有脚本的纯 Agent Skill 可以省略 manifest，但必须在 `SKILL.md` 示例段或 Brief `examples` 中至少有一个行为样例，不强制创建 `tests/` 目录。

### R7：版本化 `content_status` 完整性

新 BuildPlan 增加明确 `hash_version`：

- `hash_version=2` 的 plan hash 覆盖 `content_status`；
- 新计划只能生成 `scaffold_only`，不得由该兼容入口生成 `content_complete`；
- 没有 `hash_version` 的旧计划按 1.0 hash 兼容验证；
- legacy 计划的用户反馈保守映射为 `scaffold_only`，不能因空状态进入 completed；
- 修改 `content_status`、hash_version 或完成语义后 apply 必须拒绝。

### R8：跨宿主语义证据

Case E 不再只比较手写文件名：

- 使用一个真实 Authoring Brief 和一个真实完整候选 fixture；
- 对 Codex、Claude Code、Hermes、Pi、Kimi CLI 生成 adapter plan；
- 规范化排除 `skill_dir`、`write_tool`、`approval` 和 optional metadata 后，核心 candidate fingerprint 必须一致；
- 每个 adapter 的 target、写入工具和审批字段必须符合各自 reference；能力相同的宿主允许取值相同，差异断言只针对真实不同的宿主；
- 不调用任何宿主专用 Creator。

### R9：文档与工作区收口

- `CHANGELOG.md` 的 1.1 保持 Unreleased，直到 tag/release 获得独立授权；
- README 中英文都把官方 quick validation 标为维护者可选工具；
- 测试计数更新为实际结果；
- `kimi-hook-debug.log` 加入忽略规则但不在修复中删除用户文件；
- release log 只能陈述实际通过的门禁。

## 用户可见流程

普通用户只看到：

```text
需求已明确
→ 完整候选已准备并通过内容检查
→ 展示实际文件和行为
→ 等待确认
→ 按同一预览写入
→ 创建评审分数与边界
→ 自测
→ 真实样本试用
```

不得要求用户理解 plan id、fingerprint、Doctor runtime 或 self-test manifest；这些只作为技术详情与安全事实源。

## 测试策略

每项修复必须先增加会在当前实现上失败的回归测试，再写实现：

1. raw secret 直接保存；
2. `.env.local`、PEM、外部 symlink、路径逃逸、目录名不一致；
3. 英文写入/删除无审批；
4. `scaffold_only → content_complete` tamper；
5. legacy plan 无状态时错误进入 completed；
6. 无 CLI 环境仍能产出 portable 创建评分；
7. portable review 与 Doctor v2 parity；
8. 脚本编译成功但运行失败；
9. 自测不产生 `__pycache__`；
10. candidate/Brief/target/plan 任一漂移拒绝 Apply；
11. 五宿主 normalized candidate fingerprint 一致；
12. 普通创建路由不调用 legacy `create`。

- IR-01、IR-02、IR-03 与 NR-01、NR-02 收口；

- 核心创建流程没有 `skill-creator`、Superpowers、宿主 Creator 或独立 CLI 依赖；
- Case A–F 确定性证据通过；
- Codex 无 Creator 真实 E2E 通过；
- Hermes E2E 仍作为发布前独立环境门禁，不用 fixture 冒充；
