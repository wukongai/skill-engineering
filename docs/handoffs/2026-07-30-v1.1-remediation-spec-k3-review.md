## 本次重点评审

### 1. 范围与顺序

确认当前 Spec 是否正确保持：

```text
第一阶段：修 K3 review 阻断项并完成 Codex E2E
第二阶段：补完整 Brainstorm → Skill Spec → 程序/测试 → Skill 流程
```

不得把第二阶段悄悄塞入第一阶段，造成 1.1 修复失控。

### 2. Portable Candidate Plan

评审 `native_plan.py` 设计是否足以保证：

- preview 不写正式目标；
- Brief/candidate/target/plan 漂移阻断；
- symlink 和越界路径阻断；
- 同一未漂移计划 Apply；
- 临时目录复验后原子写入；
- 失败不伤害用户原目标；
- 无 Python 时有可审计的 Agent-native 等价路径。

重点指出是否存在 TOCTOU、目标覆盖、临时目录冲突或 plan 自身可篡改问题。

### 3. Portable Creation Review

评审以下设计是否成立：

- 单安装环境必须能得到 0–100 structural-readiness 分数和 A–F 等级；
- portable review 只覆盖可移植创建规则；
- 与完整 Doctor v2 共用维度、权重和等级边界；
- 共同支持的 fixture 要求 status、总分、grade、四维分数完全 parity；
- 高级规则未覆盖时通过 assessment coverage 明示，不能伪装已检查。

请特别判断：这是否仍然构成不可维护的“第二套评分模型”；如果是，给出更小、更稳定且不引入 CLI 安装依赖的替代架构。

### 4. 真实脚本自测安全

评审声明式 `tests/self-test.json` 和 portable runner 是否能同时满足：

- 真正执行脚本，而非只编译；
- 只执行 manifest 明确声明的候选内 Python 脚本；
- 路径、symlink、timeout、环境变量和临时副本边界；
- 不污染正式 Skill；
- 失败进入 `needs_improvement`；
- 不把任意 command 字符串变成执行入口。

请指出仍可能存在的网络、副作用、子进程或资源消耗风险，以及 1.1 最小可接受控制。

### 5. Content Gate 与脱敏

确认 Spec 是否覆盖：

- `.env*`、PEM、可解码敏感文本；
- 外部 symlink 和路径逃逸；
- frontmatter name 与目录名；
- 中英文副作用；
- 脚本与 self-test manifest 一一对应；
- `save_authoring_brief()` 在持久化边界强制脱敏。

### 6. 兼容与证据

确认：

- `hash_version=2` 是否能同时保护 `content_status` 和读取旧 plan；
- legacy plan 是否保守反馈；
- Case E 是否真的比较候选语义 fingerprint，而不是再次比较手写字符串；
- 文档发布状态不会把 1.1 提前包装成已发布。
