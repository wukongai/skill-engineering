# Handoff：v1.1.1 Maintenance Tiers & Versioning

日期：2026-08-01

状态：Ready to start

## 用户原本想完成什么

用户希望 Skill Engineering 成为创建、维护和管理 Skill 的唯一入口。更新一个
历史 Skill 时，不能因为体检发现整体结构债务，就默认要求用户先完成全量重构，
从而阻塞正在急用的小修或新功能。

下一版本需要稳定区分：

1. 紧急补丁（hotfix/patch）；
2. 范围功能升级（feature）；
3. 计划性整体重构（refactor）。

同时，普通 `improve` 维护流程需要建立真正的版本管理闭环，而不只是文档中要求
“使用语义化版本”。

## 已确认的产品缺口

当前 `improve` 的 CLI、`BuildPlan` 和 `MaintenanceRecord` 没有：

- `hotfix / feature / refactor` 维护类型；
- 紧急程度和兼容性影响；
- “阻断当前修改”与“只进入结构债务 Backlog”的分离；
- 按维护类型确定的回归范围；
- 当前版本、目标版本或 `patch / minor / major` 建议；
- 维护记录和 Changelog/版本快照的关联；
- 对 Git 分支、Commit、Push、Tag、Release 边界的结构化表达。

因此 v1.1 能保证安全修改和撤销，但不能保证每次都稳定地区分小修与整体重构，
也不能宣称普通维护已经自动完成版本管理。

## v1.1.1 目标

### 1. 维护分级决策

为每次已有 Skill 修改生成确定性、可解释的维护建议：

- `hotfix`：紧急、向后兼容、范围可隔离的错误或安全修复；
- `feature`：新增相对独立能力，默认向后兼容；
- `refactor`：结构迁移、接口重组或无法在旧架构中安全隔离的改造。

Agent 可以提出建议，但最终计划必须保存分类依据。不能只靠聊天记忆。

### 2. 阻断与技术债分离

Finding 至少区分：

- `blocks_current_change`：不修复就无法安全交付本次需求；
- `defer_to_refactor`：整体结构债务，进入独立重构任务，不阻塞本次小修；
- `informational`：只提示趋势或未来风险。

Doctor/Audit 的全局低分不能自动等价为“本次 hotfix 不允许交付”。共享安全边界、
数据丢失风险、无法回滚、破坏公开 contract 和目标漂移仍必须阻断。

### 3. 分级回归

- hotfix：本次失败回归 + 受影响 protected behavior + 共享安全 smoke；
- feature：新功能成功/失败/high-risk + 关联旧行为 + 共享门禁；
- refactor：完整回归、迁移、回滚、兼容、真实任务试用和独立评审。

production 不能没有回归证据；“分级”代表成本与范围合理，不代表降低硬门槛。

### 4. 版本管理闭环

维护计划和记录至少包含：

- `current_version`
- `recommended_bump`：`none / patch / minor / major`
- `target_version`
- `compatibility_impact`
- `release_required`
- `changelog_entry` 或明确不适用理由

SemVer 建议必须可解释：

- 向后兼容 bugfix → patch；
- 向后兼容新能力 → minor；
- 破坏公开 contract → major，并要求迁移说明。

需要定义无版本 Skill、`0.x` Skill、非 SemVer 版本和版本事实源冲突的停止行为。

### 5. Git 与发布边界

- 独立 candidate 是所有维护的最低安全边界。
- repo-managed Skill 的 refactor 默认建议独立 Git branch/worktree；hotfix 不强制
  创建分支，但不能直接在正式 source 上试错。
- Commit、Push、Tag、Release 必须继续独立确认。
- v1.1.1 不自动向 Global/Profile 安装或公开发布。

## 新任务启动顺序

1. 先读 `docs/PRODUCT.md`、`docs/constitution.md`、`docs/architecture.md`、
   `docs/TASK.md`、`docs/ROADMAP.md` 和本 Handoff。
2. 只读盘点上述维护事实源、公开 1.x contract、schema 和 release/evolution
   的版本模型；记录重复与可复用部分。
3. 创建 `docs/specs/2026-08-01-v1.1.1-maintenance-versioning-spec.md`。
4. 判断是否需要 ADR；如果改变 1.x 公开维护契约或版本事实源，必须新增 ADR。
5. 创建 `docs/plans/2026-08-01-v1.1.1-maintenance-versioning-plan.md`，按 TDD
   排列 RED/GREEN/REFACTOR 和兼容迁移。
6. 更新 TASK/Sprint 后直接进入开发；除非发现会实质改变产品范围的歧义，不要让
   用户重复回答本 Handoff 已确认的问题。
7. 使用独立候选或新任务 worktree，不在已发布/maintained source 上实验。

## 最低验收用例

1. 老 Skill 有全局技术债，但一个可隔离 hotfix 能通过目标回归并把债务延后。
2. 新增向后兼容功能，建议 `minor`，并生成对应 Changelog 条目。
3. 破坏 contract 的重构建议 `major`，要求迁移、完整回归和独立分支。
4. 安全或数据丢失问题必须阻断 hotfix，不能被 `defer_to_refactor` 绕过。
5. 无版本、非法版本和多个版本事实源冲突时安全停止。
6. 旧 1.x BuildPlan/MaintenanceRecord 可以继续读取、verify 和 undo。
7. Commit、Push、Tag、Release 没有用户明确授权时不会发生。

## 完成门禁

- 当前 Spec、Plan 和必要 ADR 完成；
- pytest、Ruff、Skill validation、production Doctor、portable self-test、
  credential lint、release consistency 和 diff check 全绿；
- 1.x 兼容、schema migration、rollback、hotfix/feature/refactor 三类真实或可信
  harness 用例通过；
- 独立评审确认没有把静态结构分包装成真实效用；
- README、Changelog、Roadmap、Task、Sprint、Version 和 Release Log 同步；
- Commit、Push、Tag 和 GitHub Release 分别等待明确授权。
