# 1.1 Native Authoring：Codex 交叉评审

评审日期：2026-07-30

评审对象：`codex/version-roadmap` 分支相对 `13045ba` 的未提交工作区（包含未跟踪的 1.1 文件）

结论：**blocked，不具备进入 Codex 真实 E2E 或 1.1 发布的条件。**

现有静态门禁全部通过，但本次最小复现确认：主创建路由仍可能落到 `scaffold_only`，Authoring Brief 持久化可写入未脱敏内容，单安装环境无法完成要求的 Doctor v2 创建评分，创建后自测没有真实执行声明脚本，Content Completion Gate 可以放过常见凭证文件变体和候选外部资源，`scaffold_only` 状态也不受计划哈希保护。这些问题直接命中 1.1 Spec 的核心验收条件，不能用 174 项单测和 Doctor 100/A 替代。

按 handoff 的“评审通过后执行 E2E”顺序，本轮没有启动 Codex 完整创建 E2E，也没有更新 Case A–F 的 Codex 状态。

## 问题列表

### CR-01 — Blocker：主创建路由仍指向只会生成骨架的 `create`，完整候选没有不可变 Apply 载体

- 文件：`skills/skill-engineering/SKILL.md:24`、`skills/skill-engineering/SKILL.md:35-36`
- 关联实现：`src/skill_engineering/scaffold.py:270-293`
- 规格：`docs/specs/2026-07-29-v1.1-native-authoring-spec.md:187-199`、`:317-325`

创建路由先要求 Agent 生成完整候选，句末又写“新建使用 `skill-engineering create`”；但该命令生成的是自己的通用 `scaffold_only` 文件，而不是接收、冻结和应用前一步完整候选。1.1 没有提供候选 manifest、Brief id/fingerprint 或可重算计划，使“用户预览的完整候选”和“实际写入内容”只能依赖宿主 Agent 自觉保持一致。

Kimi E2E 的成功路径是宿主直接把隔离候选复制到目标，并未证明 `SKILL.md` 当前声明的 `create` 主路由可以完成同一闭环。普通 Agent 按入口文字调用 CLI 时，仍可能复现“只生成骨架”的原始用户问题。

### CR-02 — Blocker：Authoring Brief 持久化边界没有强制脱敏

- 文件：`src/skill_engineering/journey.py:398-400`
- 关联实现：`src/skill_engineering/authoring.py:52-66`
- 契约：`skills/skill-engineering/references/authoring-brief.md:40-46`

`sanitize_brief()` 虽然存在，但 `save_authoring_brief()` 会直接序列化调用者传入的对象。最小复现向 `goal` 放入测试用的 `api_key=DEMO_SECRET_VALUE` 后直接保存，磁盘 JSON 中仍包含原值（`raw_secret_persisted=True`）。

脱敏是持久化安全边界，不能依赖每个宿主 Agent 或调用者记得先手动调用 helper。当前测试只验证 `sanitize_brief()` 本身，不验证落盘内容。

### CR-03 — Blocker：单安装环境无法完成强制的 Doctor v2 创建评分

- 文件：`skills/skill-engineering/references/creation-review.md:5-10`
- 关联实现：`skills/skill-engineering/scripts/doctor_skill.py:11-20`、`:31-41`
- 矛盾声明：`README.md:193-203`
- 规格：`docs/specs/2026-07-29-v1.1-native-authoring-spec.md:233-258`、`:260-282`

创建评审固定要求运行 Doctor v2 并返回 0–100 分、等级和四维明细；但是标准 Agent Skill 安装只包含薄包装器，缺少 `skill_engineering` Python 包时退出码为 2，并指导用户安装独立 CLI。仓库测试 `tests/test_doctor_wrapper.py:13-48` 还把这个行为明确固化为预期。

因此“只安装 Skill Engineering 即可完成创建评审评分”和实际安装产物不一致。Content Gate 与 self-test 的 portable 实现不能替代 Doctor v2 评分。

### CR-04 — Blocker：创建后自测把“编译成功”当成“脚本可执行”，未覆盖 Case B/F

- 文件：`skills/skill-engineering/scripts/skill_self_test.py:27-45`
- 误导文案：`skills/skill-engineering/scripts/skill_self_test.py:67-69`
- 规格：`docs/specs/2026-07-29-v1.1-native-authoring-spec.md:354-364`、`:405-415`

实现只对 `scripts/**/*.py` 调用 `py_compile.compile`，不运行脚本、不执行候选自带测试，也忽略非 Python 脚本。最小复现中，会议记录 Skill 的 `extract.py` 在空输入下真实退出 1，但 `skill_self_test.py` 仍退出 0 并报告 pass。

此外，`py_compile` 会在被测 Skill 内产生 `__pycache__`，使只读验证改变候选/正式目标。当前测试只断言 `scripts_compile == pass`，没有覆盖“声明脚本真实执行”的 Spec 条件。

### CR-05 — Blocker：Content Gate 可放过候选外部资源、常见 `.env*` 文件和目录名不一致

- 文件：`skills/skill-engineering/scripts/content_gate.py:56-69`、`:83-103`、`:143-168`
- 规格：`docs/specs/2026-07-29-v1.1-native-authoring-spec.md:201-217`

三个稳定复现：

1. 把候选中的 `scripts/extract.py` 换成指向 `/etc/hosts` 的符号链接，CG004/CG005 仍返回 pass；
2. 候选根目录名为 `demo-skill`、frontmatter name 为 `meeting-notes`，CG006 仍返回 pass；
3. 候选包含 `.env.local`，CG009 仍返回 pass，因为实现只匹配文件名等于 `.env` 或以 `.env` 结尾。

这会让非自包含候选或常见凭证文件变体进入 Apply，也与 Spec 明确要求的“目录名基线”和“.env 值不得进入候选”不一致。

### CR-06 — Blocker：`content_status` 不受不可变计划哈希保护，可绕过 `scaffold_only` 反馈

- 文件：`src/skill_engineering/scaffold.py:36-40`、`:303-312`、`:400-452`
- 状态定义：`src/skill_engineering/journey.py:153-184`

`_build_plan_hash()` 明确排除 `content_status`。最小复现中，创建计划原本是 `scaffold_only`，把该字段改为 `content_complete` 后 hash 仍有效，Apply 成功；写后反馈随即跳过骨架未完成分支，返回 completed 风格的“已按预览方案创建”。

兼容旧计划不能以牺牲新计划的状态完整性为代价。当前实现让决定用户可见完成语义的字段游离在 preview/apply 防漂移之外。

## 重要风险

### IR-01 — Important：副作用检测过窄，英文文件写入/删除可绕过 CG007

- 文件：`skills/skill-engineering/scripts/content_gate.py:39-42`、`:170-184`

当前副作用模式主要覆盖少量中文词。独立复核使用 “Write the report to disk and delete the source file” 且不包含审批的候选时，门禁仍通过。外部副作用安全不能只依赖这组关键词；结构化 contract 和 Agent 语义检查也没有形成可验证的统一结果。

### IR-02 — Important：Case E fixture 没有验证跨宿主候选语义一致

- 文件：`skills/skill-engineering/tests/host-adapter-fixtures.yaml:5`
- 测试：`tests/test_host_adapters.py:34-39`

fixture 只在五个手写 host 条目里重复相同文件名，测试没有生成或加载五份候选，也没有比较规范化内容/fingerprint。因此它证明了 adapter 文档清单存在，不能证明 Spec 要求的“同一 Brief 在五个宿主中核心文件语义一致”。

### IR-03 — Important：1.1 Changelog 已形成正式发布外观

- 文件：`CHANGELOG.md:3-15`
- 对照：`docs/releases/RELEASE-LOG.md:5-11`

发布日志仍说明 1.1 门禁未通过，但 Changelog 已出现带日期的正式 `1.1.0` 章节。发布授权前应保持 Unreleased 语义，避免用户或自动化把未通过版本识别为已经发布。

## 放行条件

1. 主创建路由不再把完整候选导向 `scaffold_only create`；为 Native Authoring 建立候选 manifest、Brief/fingerprint 和同一预览计划 Apply 的可验证载体。
2. 在 `save_authoring_brief()` 等持久化边界强制脱敏，并用落盘内容回归测试证明原始敏感值不会保存。
3. 单安装产物能够完成 Spec 要求的 Doctor v2 创建评审评分，或在 Spec/产品承诺层面重新定义且保持一致；不能一边承诺无 CLI，一边在固定步骤要求 CLI。
4. 自测真实运行所有声明脚本/测试入口，并分别报告确定性层与样例任务层结果；验证不得污染被测目录。
5. Content Gate 拒绝 symlink/越界解析、所有 `.env*` 变体和目录名/frontmatter name 不一致，并增加先失败、后修复的回归测试。
6. `content_status` 和其它决定完成语义的字段纳入新计划完整性校验，同时保留旧计划的显式版本兼容。
7. 修复后重新运行完整静态门禁与本评审最小复现；评审通过后再执行 handoff 规定的 Codex 真实 E2E。
