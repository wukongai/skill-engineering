日期：2026-07-31

## 一、结论

Skill Engineering v1.1 已经通过项目自身全部工程门槛，并在阿里 Skill Up 驱动的真实 Codex 环境中完成 4/4 个核心行为场景。按照当前“Codex 是发布硬门槛，其他 Agent 是非阻断兼容性证据”的发布政策，v1.1 可以进入发布流程。

微软 Waza 的结果不应简单记作“25% 能力通过率”。其首轮单回合评估中，两个创建场景按照 Skill Engineering 的安全契约停在 `candidate_ready`，等待用户批准后才允许写入正式目标；Waza 的单回合文件评分器则立即检查正式目录，因此将这两个安全停顿判为失败。修正为多回合批准流程后，GitHub Copilot 月度额度耗尽，正式 Apply 阶段未能跑完。

Waza 仍然发现了两个值得进入后续修复的真实问题：

1. 在 Copilot 主机中，“一次只问一个问题”没有稳定执行，Agent 在主问题后又列出了多个带问号的示例问题。
2. 根 `SKILL.md` 为 2,421 tokens，高于 Waza 默认的 500-token 入口预算；这不影响当前 Codex 发布，但表明跨 Agent 的入口精简和渐进披露仍有优化空间。

因此，本次评估支持以下判断：

- **Codex 发布判断：通过。**
- **v1.1 工程质量：通过。**
- **四个核心场景在真实 Codex 中的可用性：通过，但仅限本次场景组合。**
- **跨 Agent 普适性：尚不能宣称；Waza 结果为部分证据且未完成。**
- **是否可以发布：可以，但 Commit、Push、Tag、Release 仍是各自独立的显式授权点。**

### 5.2 评估环境发现

Skill Up 的非交互 Codex 执行需要明确的主机隔离配置：

- 测试提示要求仅使用 `skill-engineering`，避免环境中其他全局 Skill 自动参与。
- 使用 `bypass_sandbox=true`，否则非交互执行无法处理 Codex 的文件/命令批准请求。

一次无效运行曾自动加载全局 Superpowers 相关 Skill 并发生超时。这是宿主环境污染，不是 Skill Engineering 的产品依赖。有效运行已经隔离，结果证明 v1.1 不依赖 Skill Creator 或 Superpowers 才能完成四个场景。

评估脚本中还修正了两个判定器问题：中文问号的 UTF-8 字节计数，以及“不执行”同义表达未被维护场景规则接受。这两项属于测试 Harness 修复，不计入产品缺陷。

## 六、Microsoft Waza

### 6.1 静态检查

Waza `check` 的主要结果：

- agentskills.io 的 frontmatter、字段、目录名和安全检查通过。
- Waza 综合就绪结论为 `ready: false`，compliance level 为 Low。
- 根 `SKILL.md` 为 **2,421 tokens**，超过 Waza 默认 **500 tokens** 的硬预算。
- Waza 认为 24 个 reference 模块是 orphaned。实际根文件使用反引号代码路径进行路由，而 Waza 主要识别 Markdown 链接，因此这是工具识别差异，同时也提示跨工具链接形式可改进。
- Waza 扫描到了测试 fixture `meeting-notes`，说明仓库级发现需要排除测试夹具，否则 Skill 清单可能被污染。
- 正向项包括渐进披露、范围收敛、无明显负向 delta 和无过度特化。

入口 token 超限是一个真实的跨 Agent 可移植性信号，但 Waza 的 500-token 标准不能机械替代 Skill Engineering 自身的编排需求。后续应通过“更薄的入口 + 明确路由 + 参考模块链接”降低成本，同时保留完整创建能力。

### 6.2 GitHub Copilot 行为评估

Waza 首轮四场景单回合运行：

- 总场景：4
- Waza 记录成功：1
- Waza 记录失败：3
- 原始成功率：25%
- 汇总分：约 0.771
- 时长：约 6 分 15 秒

这个 25% 不能直接当作 Skill Engineering 的真实能力通过率：

- 完整创建和外部副作用两个场景都生成了详细候选与 Preview，并按产品安全契约停在 `candidate_ready`，等待显式批准。
- Waza 的单回合文件评分器立即检查正式目标，因此“未绕过批准直接写文件”被判成文件缺失。
- 这两个结果证明批准前停止有效，但没有证明批准后 Apply 成功。

有一个明确的真实行为失败：

- 模糊需求场景虽然没有提前写文件，但 Copilot 在一个主问题之后又列出四个带问号的示例问题，未满足“一次只问一个问题”。

维护场景的首轮结果受 fixture 路径错误影响，不能作为有效的真实修复结论。

随后已将 Waza 配置改为多回合流程：第一回合生成计划，第二回合明确批准同一计划，并修正维护 fixture 路径。但运行期间 GitHub Copilot 返回 HTTP 402 `quota_exceeded`，创建和高风险场景没有完成 Apply。维护内容评分器在正确 fixture 上通过，但整个会话仍因额度错误终止，因此只能记为部分证据。

本次没有使用 mock 填补 Waza 结果，也不把额度错误伪装成产品通过或失败。

## 八、问题等级与后续建议

### P1：强化“一次只问一个问题”的跨 Agent约束

当前规则在 Codex 中通过，但 Copilot 会把示例选项写成多个问题。建议：

- 明确禁止在同一回合的示例、括号、列表中继续使用问句。
- 把备选项改成陈述式选项，不使用问号。
- 增加一个跨主机回归评分器，按 Unicode 问号和语义问句共同检查。

这不是当前 Codex 发布阻断项，但属于 1.1.x 的优先兼容性修复。

### P1：降低入口重量

根 `SKILL.md` 目前承担较多编排说明。建议在不削弱完整创建能力的前提下：

- 将细节继续下沉到 stage/reference 文件。
- 根入口只保留触发条件、总流程、强制安全门和路由表。
- 为关键模块使用可被更多工具识别的 Markdown 链接。
- 建立入口 token 预算回归检查，但不要未经验证地机械采用 500 tokens 作为唯一标准。

### P2：补齐第三方 Harness 兼容说明

- 记录 Skill Up 非交互 Codex 所需的单 Skill 隔离与批准处理方式。
- Waza 仓库扫描时排除测试 fixture。
- Copilot 额度恢复后重新执行多回合 Apply，不回滚到单回合绕过批准。

### P2：控制执行成本

四个 Skill Up 场景约 18 分 26 秒，输入 token 报告量较高。建议在 1.1.x 或 1.2 中检查：

- 是否重复加载相同 reference。
- Doctor、Content Gate、自测是否存在可安全合并的重复扫描。
- 简单模糊需求场景是否能在入口层快速停止，避免进入完整工程流水线。

## 九、发布判断

基于当前发布政策：

1. Codex 是默认且唯一的真实主机发布硬门槛。
2. 项目自身工程门槛全部通过。
3. Skill Up 驱动的真实 Codex 四场景全部通过。
4. Waza/Copilot 作为非阻断兼容性证据，发现的问题已明确记录，不需要把额度耗尽或安全批准停顿升级为 v1.1 发布阻断。

**结论：Skill Engineering v1.1 可以进入 Commit、Push、Tag 和 Release 流程。**

但本报告不自动授权这些外部状态变更；每一步仍需遵循仓库的独立审批规则。

## 十、证据限制

- Skill Up 没有执行“无 Skill 基线”或 A/B 对照，因此不能量化 Skill Engineering 相对裸 Agent 的提升幅度。
- 四个场景各自只完成有限次数运行，不代表统计稳定性。
- 共同场景集不是独立 holdout，不能宣称普遍效用。
- Waza 多回合批准后的 Apply 被 Copilot 额度阻断，跨主机结论不完整。
- 三个框架的分数定义不同，不应合成为单一总分。
- 当前最准确的效用声明是：**v1.1 在本报告四个核心场景的真实 Codex 运行中获得支持；跨 Agent 效用仍需继续验证。**
