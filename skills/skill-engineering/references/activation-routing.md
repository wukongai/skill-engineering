# 自然语言激活与承接

[返回根入口](../SKILL.md) · [文件地图](file-map.md) · [开发案例](../tests/activation-cases.json)

用户创建、维护或检查 Agent Skill 时，不需要说出 Skill Engineering 名称，也不需要使用固定激活词。技能包、可复用 AI 指令流程、反复调用的小助手，都可能表达相关需求；先判断任务对象和动作，再进入既有能力流程。

## 对象与上下文

1. 用户显式选定其他 Skill 或工具时，尊重该选择。需要补充能力时说明缺口，不自行替换用户已选工具。
2. 先复用上文已确认的对象、用户提供的文件或路径。需要时只读检查当前目录的入口和约束；一份 `SKILL.md` 的存在只是对象线索，仍需判断用户是在工程化它，还是用它完成业务。
3. 对象已确认是 Skill 时，“上回这个又跑偏了”“把这个补一下”“先看看这份靠不靠谱”等口语、近义词和省略表达，按当前动作承接。不要再次要求用户说产品名或重复已知对象；动作或必要输入仍缺失时，只问会改变结果的问题。
4. 对象仍未知时，只问一个对象问题，例如“你说的‘这个’具体指哪份内容或哪类可复用能力？”等待回答后再判断路线，不默认创建候选、写入、安装或发布。
5. 用户只表达“以后一句话反复用的小助手”等构想时，进入发现流程，先澄清实际任务与复用需求；尚未决定产物类型前不默认新建 Skill。

## 承接到原流程

| 用户意图与常见表达 | 后续入口 |
|---|---|
| 创建、编写、封装技能包或可复用指令流程；构想反复使用的小助手 | [能力探索](capability-brainstorming.md)、[产物选择](selection-matrix.md)和[发现阶段](../stages/discover/INSTRUCTIONS.md)；确认需要 Skill 后回到根入口的 Native Authoring 路线。 |
| 修改、补能力、升级、重构、越改越乱，或已有 Skill 调用失败 | [维护协议](maintenance-protocol.md)和[维护审查阶段](../stages/review/INSTRUCTIONS.md)；沿用原架构审查与同一维护计划。 |
| 检查、评审、体检、测试、排查 Skill 的入口、边界、架构、失败处理或行为 | [检查阶段](../stages/doctor/INSTRUCTIONS.md)；涉及真实行为比较时再读[评测规范](evaluation-standard.md)和[评测阶段](../stages/evaluate/INSTRUCTIONS.md)。 |

激活只决定读取哪套已有流程。创建仍需发现与 Native Authoring，维护仍需隔离候选和架构门；预览、同一计划应用、验证和审批边界按[根入口](../SKILL.md)执行。模糊表达本身不构成写入批准，既有有效授权也不因换一种说法而丢失。

## 反触发

| 实际任务 | 承接方式 |
|---|---|
| 用现成领域 Skill 整理会议、生成图片或完成其他业务 | 使用对应能力完成业务，不启动 Skill 工程维护。 |
| 检查或修复普通程序、润色文案、审稿 | 保持原任务；“改一下”“检查”本身不是 Skill 对象证据。 |
| 只解释 Skill、MCP、提示词的区别，或学习演讲等人的技能 | 回答概念或学习问题。 |
| 只做项目 harness、Claude/Codex 入口、tmux 项目墙或开工自检 | 保持既有工程入口范围。 |
| 用户显式指定其他 Skill/工具处理创建或修改 | 遵从用户选择，不宣称本 Skill 抢占或覆盖宿主选择器。 |

## 证据边界

预加载描述帮助宿主发现；此参考在根入口被读取后指导承接，不能保证或覆盖宿主选择器。开发案例均为合成输入，仓库测试只检查元数据、链接、覆盖和案例合同，不执行语义分类。真实自动选择须另行观察宿主成功读取根 `SKILL.md` 正文；目录列表、描述命中和模型自报都不足以证明激活，更不能证明实际任务效用。
